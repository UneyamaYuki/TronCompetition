# 本システムの実装計画

## 概要

本システムは、金魚に対する給餌行動を監視することにより、高齢者自身への監視感を軽減しつつ孤独死を未然に防ぐことを目的としている。

開発者自身の身内で熱中症により倒れ、3日間誰にも気づかれなかった事案があった。すんでのところで一命を取り留めたが、そのような事案を未然に防げないかと考案したシステムである。

対象者を金魚としており、カメラを水槽に向けて設置されることを期待している。基本的には画角内に常に金魚が存在するものとしている。また、汎用性を高めた金魚ではなく、自宅で飼育している私個人の金魚を検出対象としている。(サンプルとして完成させるため、かなりスコープを絞った前提を置いていること、ご了承ください。)

システムとしては、同期駆動で5fps駆動で実装を行った。これは、餌の沈降速度を確実に検知できる、かつ、マイコンの処理性能上限に至らないような駆動レート設定である。まずカメラで映像を取得したのち、NPU側では「金魚検出」・CPU側では「餌検出」が行われる。その2つの結果が統合されて「給餌判定」および「給餌空白期間判定」が行われるシステムとなっている。

このような動作により、給餌が行われていない期間を検知して、飼い主の異常の可能性を検知するプロダクトとなっている。

## 機能実装

### 金魚検出

当初の計画では、金魚検出にEK-RA8P1に搭載されたEthos-U55 NPUを使用する。OV5640から取得した640x480画素のRGB565画像を入力フレームとし、CPU側でグレースケール化したうえで256x256画素へリサイズする。この画像をINT8量子化した軽量な単一物体ボックス回帰モデルへ入力し、金魚1匹のバウンディングボックス（左上座標$x$、$y$、幅$w$、高さ$h$）と検出確信度を出力する。座標は入力画像の幅と高さで正規化し、後段の餌候補との距離計算に利用する。

モデルは小型の畳み込みニューラルネットワークを基本とし、MobileNetV2系の軽量な構成を候補とする。Ethos-U55で実行できるよう、学習後にFull INT8量子化を行い、TFLite Microへ組み込む。実機ではμT-Kernel 3.0のタスクからRUHMIおよびEthos-Uドライバを介してNPUを起動し、200ms周期、すなわち5回/秒で推論する。入力テンソルは`[1, 256, 256, 1]`、出力テンソルは`[1, 5]`とし、検出確信度が初期値0.5以上の場合に金魚検出結果を有効とする。

この初期方針に従い、MobileNetV2系ではImageNetによる学習済み重みを利用したファインチューニングでモデルを用意した。学習データおよびオフラインの性能評価では十分と言える結果が得られたが、実機確認を行うと検出枠の破綻が頻出した（実機ではほとんど正常に検出できなかった）。そこで、実機での検出安定性を優先し、ベースモデルをYOLOv5sへ切り替える実装を行った。以下に、切り替え前後のモデル仕様と同一20枚での評価結果を示す。

切り替え後の現行実装では、カメラ画像をRGB888へ変換してletterbox処理を行い、YOLOv5sへ入力する。入力テンソルは`[1, 256, 256, 3]`の`uint8`、出力テンソルは`[1, 4032, 6]`の`uint8`である。出力の6要素は`center_x`、`center_y`、`width`、`height`、`objectness`、`class_score`であり、実数化した`objectness * class_score`を検出スコアとする。スコア閾値0.5で候補を絞り、IoU閾値0.45のNMSを行った後、画面中心に最も近い検出枠を金魚枠として採用する。モデル重みはFull INT8量子化されているが、実機の入出力テンソル型は`uint8`である。

|---|---|---|
| 入力 | グレースケール、`[1, 256, 256, 1]` | RGB、`[1, 256, 256, 3]` |
| 出力 | `[1, 5]`（1枠の座標と確信度） | `[1, 4032, 6]`（4032候補の座標、objectness、class score） |
| 量子化 | INT8 | Full INT8量子化、実機テンソルは`uint8` |
| 学習用TFLiteファイル | 654,616 bytes（0.624 MiB） | 7,367,840 bytes（7.027 MiB） |
| 実機への配置 | 内部Flashへ組み込み | OSPI0 CS1へ配置し、起動時にSDRAMへコピー |
| 同一20枚の平均IoU | 0.4281 | 0.6280 |
| IoU 0.5以上 | 7/20枚 | 16/20枚 |
| 20枚中の検出成功 | 単一枠を出力するが、実機では枠位置の破綻が頻出 | 20/20枚で少なくとも1件を検出 |

SDRAM にモデルを読みだして、推論ごとに利用するデメリットは、餌検出やLCD描画と帯域ひっ迫を起こす可能性があることである。実際、ディスプレイを見ていると、たまにチラついて見えることがある。ただし、今回はこれに対処する時間が無かったのと、システムの動作には影響はないものとして許容した。

検出結果は同じフレームに対する餌検出処理へ渡し、金魚の位置と餌候補の中心位置との距離、および距離の時間変化を給餌判定に利用する。確信度が閾値を下回った場合やボックス追跡が途切れた場合は、金魚が存在しないと断定せず、給餌判定を`unknown`として扱う。これにより、金魚の見失いを給餌完了や未給餌と誤って解釈しないようにする。

LCDにはカメラ映像を表示し、金魚を検出できたフレームでは採用したバウンディングボックスを緑色の枠で重ねて表示する。検出できない場合は金魚枠を表示せず、前回の枠を残さない。LCD上にはYOLOの確信度やIoUの数値は表示せず、枠の有無を金魚検出結果の確認に用いる。

### 餌検出

餌検出は、餌が小さく形状も一定しないことから、NPUによる物体検出モデルではなく、Cortex-M85上のCPU画像処理として実装する。固定ROIには依存せず、640x480画素の画面全体を対象とする。カメラから得たRGB565フレームを8ビットグレースケールへ変換し、現在フレームと直前フレームの画素ごとの差分の絶対値を求める。その差分量の上位2%を初期の動き閾値として二値化し、3x3画素のモルフォロジー処理で孤立ノイズを除去する。

二値画像から連結成分を抽出し、面積が3画素未満の成分や、魚の移動・水槽全体の明るさ変化に相当する大きすぎる成分を除外する。餌の輪郭が分断された場合は、中心間距離が12画素以内の成分を統合して一つの餌候補とする。待機状態では、8ビットRGBへ変換した暖色成分も候補の発見に利用し、初期値として`min(R,G)-B > 15`、`max(R,G) < 210`、`min(R,G) > 20`を用いる。ただし、色や単発の画素差分だけでは餌とは確定しない。

餌候補はフレーム間で中心位置、面積、差分強度を対応付け、少なくとも2回連続して同一候補の追跡が成立し、かつ時間方向に下へ移動している場合に`food_sinking`として確定する。移動量はフレーム間隔で正規化し、5fpsの実機動作とデータ収録時の実測間隔を混同しないようにする。速度、横方向の移動量、面積および差分強度が設定した物理範囲を外れた場合は候補のまま保持し、餌として扱わない。

カメラ振動や照明変化により画面全体の差分が過大になった場合、追跡が長時間途切れた場合、餌候補が底面で停止した場合は、餌の消失だけを根拠に給餌完了とはしない。必要に応じて2フレーム前との差分を対応付けの補助に用いるが、それだけで餌確定へ遷移させない。これにより、泡、ゴミ、反射、魚の自発的な遊泳および照明変化による誤検出を抑制する。

餌候補が存在し、候補中心の座標が有効な場合は、LCD上のカメラ映像に候補中心を囲む黄色の約10x10画素の枠を表示する。この枠は初期候補や追跡中の候補にも表示されるため、黄色枠だけでは給餌完了を意味しない。餌候補がない場合、または座標が無効な場合は餌枠を表示しない。餌の確定状態や沈下速度の数値はLCDには直接表示せず、給餌状態表示と組み合わせて確認する。

### 給餌判定・給餌空白期間判定

給餌判定は、NPUが出力した金魚ボックスと、CPUが追跡した餌候補を同一フレーム時刻で統合して行う。状態は`IDLE`、`FOOD_CANDIDATE`、`TRACKING`、`FOOD_CONFIRMED`、`FISH_APPROACHING`、`EATING_CANDIDATE`、`FEEDING_COMPLETED`の順に管理する。まず画面全体から餌候補を取得し、前フレームとの差分で同一候補の対応付けを行う。連続した下降軌跡が成立した候補だけを確定済みの餌とし、その後に金魚ボックスとの距離が縮小したことを確認する。

LCDに表示する給餌状態の意味は次のとおりである。

| 状態 | 意味 |
|---|---|
| `IDLE` | 餌候補を追跡していない待機状態。 |
| `FOOD_CANDIDATE` | 餌らしい候補を検出したが、沈下軌跡はまだ確定していない状態。 |
| `TRACKING` | 餌候補をフレーム間で追跡し、沈下の継続を確認している状態。 |
| `FOOD_CONFIRMED` | 連続した下降軌跡が成立し、餌として確定した状態。 |
| `FISH_APPROACHING` | 確定した餌へ金魚が接近している状態。 |
| `EATING_CANDIDATE` | 餌が金魚の近傍で見えなくなり、または重なり条件の確認中で、給餌完了を保留している状態。 |
| `FEEDING_COMPLETED` | 餌の消失確認、または方向一致した餌と金魚の重なりを確認し、給餌完了と判定した状態。 |
| `UNKNOWN` | カメラ、金魚または餌の追跡が成立せず、判定できない状態。 |

確定済みの餌候補が金魚の近傍で消失した場合は、直ちに給餌完了とはせず、`EATING_CANDIDATE`へ遷移する。消失後、一定時間にわたって餌候補が再出現しないことを確認できた場合に`FEEDING_COMPLETED`へ遷移する。一方、餌候補が検出ノイズとして残っていても、餌と金魚が互いに近づく方向の移動を示し、餌中心が金魚ボックスと重なった場合は、消失を待たず`FEEDING_COMPLETED`へ遷移する。いずれの場合も、餌候補の沈下軌跡が成立しない場合、餌が底面に残った場合、または金魚・餌のどちらかの追跡が途切れた場合は給餌完了としない。

判定不能な状態は`unknown`として記録し、給餌完了時刻を更新しない。これには、カメラ振動や照明変化による差分の増大、餌候補の一時的または長時間の見失い、金魚に隠れた後の再出現確認不能、底面残留などを含める。`unknown`は未給餌アラートとは区別し、画像から判定できない状態としてLCDに表示する。

給餌完了時刻と監視経過時間はCPU側で管理し、最後に確認できた`FEEDING_COMPLETED`からの経過時間を5fpsの判定ループとは独立した時刻基準で計測する。通常運用では3日間給餌完了が確認されない場合に未給餌アラートとし、動作確認時は設定により10分間へ短縮する。再起動後も計測を継続できるよう、最後の給餌時刻と有効な時刻基準を保持する。時刻が未設定または無効な場合は未給餌と断定せず、監視時刻不明として判定を保留する。

実機では、デバッグ状態、給餌完了、未給餌アラートおよび`unknown`をLCDへ表示する。検出、時刻管理および状態機械はEK-RA8P1上で完結させ、PCは学習、モデル変換およびオフライン評価に限定する。外部通信による通知は今回の実装対象に含めず、まずは給餌完了の見逃しと誤完了を実機映像で評価する。

LCD上部には状態表示帯を設け、1行目に`FEED: <給餌状態>`、2行目に`GAP: <給餌空白期間の状態> <経過秒数>S`を表示する。給餌状態は`IDLE`、`FOOD_CANDIDATE`、`TRACKING`、`FOOD_CONFIRMED`、`FISH_APPROACHING`、`EATING_CANDIDATE`、`FEEDING_COMPLETED`または`UNKNOWN`のいずれかである。給餌空白期間の状態は`TIME_UNKNOWN`、`MONITORING`または`ALERT`であり、時刻不明時は経過秒数を`--S`と表示する。

給餌空白期間の状態の意味は次のとおりである。

| 状態 | 意味 |
|---|---|
| `TIME_UNKNOWN` | 有効な時計または最後の給餌時刻がなく、経過時間を判定できない状態。 |
| `MONITORING` | 最後の給餌確認からアラート基準時間に達していない監視中の状態。 |
| `ALERT` | 最後の給餌確認からアラート基準時間を超え、未給餌の可能性を通知する状態。 |

状態表示帯の色は、通常監視中の`MONITORING`をシアン、給餌完了の`FEEDING_COMPLETED`を緑、未給餌アラートの`ALERT`を赤、`UNKNOWN`または`TIME_UNKNOWN`を黄色とする。未給餌アラートが成立した場合はアラート色を優先する。これにより、映像上の金魚枠と餌候補枠に加え、給餌判定の現在状態、給餌完了からの経過時間、未給餌アラートまたは判定不能状態をLCDだけで確認できる。

## メモリ利用・帯域利用戦略

このシステムでは、画像、表示、NPU推論用のバッファをすべて内部RAMへ置くことはできない。そのため、容量の大きいデータは外部SDRAMへ置き、CPUとDMA、GLCDC、Ethos-U55が同じバッファを共有する。ここでは、メモリ容量の問題と、1秒間にどれだけデータを読み書きするかという帯域の問題を分けて管理する。

### メモリ領域の使い分け

| 領域 | 主な用途 | 現行実装での配置方針 |
|---|---|---|
| 内部RAM / TCM | μT-Kernel、スタック、制御変数、餌検出の小さな作業配列 | 低遅延が必要な制御処理と小容量データを配置する。 |
| SDRAM `.sdram_noinit_nocache` | VINカメラバッファ、GLCDC表示フレームバッファ | DMAとGLCDCが直接アクセスするため、キャッシュを介さない領域に置く。 |
| SDRAM `.sdram_nocache` | TFLite Microのテンソルアリーナ、SDRAMへコピーしたモデル | NPUとCPUが共有するため、キャッシュ整合性の問題を避ける。 |
| OSPI0 CS1 | YOLOv5sのモデルデータの不揮発保存 | 起動時に読み出すだけの保存領域とし、推論時はSDRAM上のコピーを使用する。 |

現行リンクマップでの容量は次のとおりである。

| データ | 計算 | 容量 |
|---|---:|---:|
| VINバッファ3面 | `1280 bytes x 600 lines x 3` | 2,304,000 bytes（約2.20 MiB） |
| 表示フレームバッファ2面 | `1024 x 600 x 2 bytes x 2` | 2,457,600 bytes（約2.34 MiB） |
| YOLOモデルのSDRAMコピー領域 | `7 MiB`確保 | 7,340,032 bytes（7.00 MiB） |
| TFLiteテンソルアリーナ | `1536 KiB`確保 | 1,572,864 bytes（1.50 MiB） |
| SDRAMリンク使用量 | 上記のリンクセクション合計 | 13,674,496 bytes（約13.04 MiB） |

VINの実画像は640x480 RGB565であるが、DMAバッファは1行1280 bytes、600行として確保されている。したがって、画像の有効部分は1フレーム614,400 bytesであり、バッファ全体は768,000 bytesとなる。600行の設定と1280 bytesのストライドは、VINドライバの設定と一致させる必要がある。

EK-RA8P1ボードの外部SDRAMは64 MiBであり、現行の使用量には十分な余裕がある。ただし、現在の生成済みリンカ設定はSDRAMのアドレス範囲を128 MiBとして宣言している。将来バッファを増やす場合は、リンカが許していても物理的な64 MiBを超えないことを必ず確認する。OSPI0 CS1についても、リンクマップ上のアドレス空間の大きさと、ボードに搭載された実際のフラッシュ容量を混同しない。

### キャッシュとアラインメント

カメラのVIN DMAはフレームを書き込み、CPUは同じフレームを読み、GLCDCは表示フレームバッファを読み続ける。このように複数のマスタが同じメモリを使う場合、CPUキャッシュに古いデータが残ると、カメラ画像の一部だけ古いまま表示されたり、推論と表示で異なるフレームを参照したりする可能性がある。そのため、現行実装では次のバッファを非キャッシュSDRAMへ配置する。

- `vin_image_buffer_1`〜`vin_image_buffer_3`: VIN DMAの書き込み先
- `g_display_framebuffers[2]`: GLCDCの表示用ダブルバッファ
- `g_tensor_arena`: TFLite MicroおよびEthos-U55が使用するテンソル領域
- `g_model_sdram_copy`: OSPIからコピーした推論モデル

バッファはDMAやNPUの要求に合わせて64 bytesまたは128 bytes境界にアラインメントする。カメラバッファは生成設定により128 bytes、表示・NPU用バッファは実装により64 bytes境界へ配置している。これらのセクション名、アラインメント、キャッシュ属性は、FSPの生成設定とリンカスクリプトを変更した際に同時に確認する。

### 1フレームのデータの流れ

1. OV5640からのフレームをVIN DMAが3面のリングバッファのいずれかへ書き込む。
2. CPUが最新のRGB565フレームを使い、256x256x3のRGB入力テンソルを作成する。上下のレターボックス部分は画像データを読み込まず、入力を0で埋める。
3. Ethos-U55がSDRAM上のモデルコピーとテンソルアリーナを使って金魚推論を実行する。
4. CPUの餌検出は、640x480全体を4分の1に縮小した160x120グリッドを読み、前フレームとの差分を計算する。餌検出専用の640x480フルサイズ作業画像は追加確保しない。
5. 表示処理が最新フレームを表示用バックバッファへコピーし、金魚枠・餌枠・状態表示を重ね描きする。GLCDCの表示更新可能なタイミングでフロントとバックを交換する。

モデルは起動時にOSPIからSDRAMへ一度だけコピーする。したがって、約6 MiBのモデルデータを毎フレームOSPIから読み出す設計ではない。推論中の主な共有先はSDRAM上のモデルコピー、テンソルアリーナ、カメラバッファ、表示バッファである。

### 帯域の概算

5 fpsで動作した場合の、代表的なメモリアクセス量を次に示す。これはバスの実効帯域ではなく、プログラムが要求するデータ量の概算である。キャッシュ、バースト転送、DMAの待ち時間、表示タイミングは含まない。

| 処理 | 1フレームあたりの概算 | 5 fpsでの概算 |
|---|---:|---:|
| VIN DMAのフレーム書き込み | 768,000 bytes | 3,840,000 bytes/s（約3.66 MiB/s） |
| 表示用コピー（カメラ読み出し + 表示バッファ書き込み） | 1,228,800 bytes | 6,144,000 bytes/s（約5.86 MiB/s） |
| 餌検出のRGB565読み出し | 38,400 bytes | 192,000 bytes/s（約0.18 MiB/s） |
| NPU入力テンソルへの書き込み | 196,608 bytes | 983,040 bytes/s（約0.94 MiB/s） |

NPU入力のリサイズでは、実装上、256x192の画像領域についてRGB565の補間元を複数回読み出す。単純計算では読み出しが最大約1,179,648 bytes/フレームとなるため、入力変換は餌検出そのものよりメモリアクセス量が大きい。GLCDCは5 fpsではなくパネルの表示周期で表示バッファを読み続ける。パネルを60 Hzで駆動した場合、`1024 x 600 x 2 x 60` に相当する約70.3 MiB/sの読み出しが発生するため、表示系は常時帯域を消費する経路として扱う。

### 現時点のボトルネックと運用ルール

現行構成では、モデルのOSPIからSDRAMへのコピーは起動時だけなので、通常の5 fps処理の帯域ボトルネックではない。注意すべきなのは、パネル表示の連続読み出し、カメラフレームのDMA、CPUによるRGBリサイズと表示コピーが同じSDRAM系統を共有することである。表示のちらつきや推論周期の乱れが発生した場合は、まずGLCDCのアンダーフロー、VINのフレーム通知遅延、NPU推論時間、表示コピー時間を個別に計測する。

今後の変更では、次のルールを守る。

- 640x480 RGB565のフルサイズ作業バッファを新たに増やさず、既存のVINバッファを再利用する。
- VIN DMAが書き込み中のバッファをCPUやGLCDCが読まないよう、バッファの所有権とフレーム番号を確認する。
- カメラ、表示、NPUの共有バッファを通常のキャッシュ可能RAMへ移さない。移す場合は、DMA前後のキャッシュフラッシュ・無効化を設計に追加する。
- テンソルアリーナを小さくする場合は、TFLite Microの初期化ログで必要サイズを確認してから変更する。経験だけで削ると、モデル変更時に実行時エラーになる。
- ビルド後はリンクマップで各セクションの開始アドレスとサイズを確認し、物理SDRAM 64 MiBの範囲内であることを確認する。

評価時には、推論の5 fps周期が維持できているか、表示更新のタイムアウトやアンダーフローが増えていないか、VIN/NPUのエラー通知が増えていないかを同時に記録する。メモリに収まることと、5 fpsで処理が間に合うことは別条件であり、両方を満たして初めて実機で安定して動作すると判断する。

## μT-Kernel 活用戦略

本システムでは、μT-Kernel 3.0をアプリケーションの起動、周期実行、待ち合わせおよび時刻管理に使用する。RTOSの機能自体を主な工夫として競う構成ではなく、カメラ取得、NPU推論、餌検出、給餌判定および表示更新の順序を崩さずに実行することを優先した。そのため、複数の処理タスクを細かく分割するのではなく、推論を中心とした同期処理タスクを1つ配置している。

### タスク構成

`usermain`で金魚検出・給餌監視タスクを1つ生成し、優先度10、スタック16 KiBで起動する。タスク起動後の`usermain`は待ち状態に入り、アプリケーション処理と同じ処理を二重に実行しない。タスクの初期化処理では、Ethos-U55、OSPIモデル保存領域、SDRAM上のモデルコピー、TFLite Micro、カメラおよび表示を順に初期化する。初期化に失敗した場合はエラーを出力して無期限待ちに入り、未初期化のモデルやバッファを使って処理を続行しない。

### 200ms周期の維持

推論タスクは、カメラ入力の準備、Ethos-U55推論、YOLO後処理、餌検出、給餌状態機械およびLCD更新を1回の処理単位として実行する。各ループの開始時刻を`tk_get_otm`で取得し、処理終了後に経過時間を差し引いた残り時間だけ`tk_dly_tsk`で待つことで、処理時間を含めて約200ms周期、すなわち5fpsを目標とする。カメラフレームがまだ完成していない場合は10msだけ待って再確認し、CPUを空転させない。

この構成では、カメラ取得と推論を別タスクへ分割してキューで接続する方式は採用していない。フレームの所有権やキュー滞留による遅延を増やさず、同一フレームに対する金魚検出と餌検出を同じ周期内で処理するためである。カメラの再取得は、推論・表示・給餌判定が完了した後に次のフレームを再アームする。

### NPU待ち合わせとセマフォ

Ethos-Uドライバが要求するミューテックスと推論完了通知は、μT-Kernelのセマフォで実装している。ミューテックスは`tk_wai_sem`と`tk_sig_sem`で排他制御を行い、NPUの推論完了通知は初期カウント0のセマフォをドライバコールバックから`tk_sig_sem`で通知し、推論タスク側が`tk_wai_sem`で待ち合わせる。これにより、NPU処理中に推論タスクが完了をポーリングし続けることを避けている。推論完了待ちには最大2秒のタイムアウトを設定し、タイムアウト時はNPUレジスタを出力して原因を調査できるようにする。

### 時刻と状態機械の扱い

給餌判定には、推論タスクの周期回数ではなく`tk_get_otm`で取得した単調増加時刻を渡す。餌候補のフレーム間速度、追跡タイムアウト、餌消失後の確認時間および最後の給餌からの経過時間を同じ時刻基準で計算するため、処理時間の揺らぎやカメラフレームの欠落を給餌完了と誤認しにくい。実時刻が有効な場合は単調時刻との基準を対応付け、実時刻が未設定または不整合な場合は未給餌アラートを確定せず、`TimeUnknown`として扱う。

以上のように、本実装でのμT-Kernel活用の要点は、複雑なタスク分割ではなく、単一の同期処理タスク、明示的な周期待ち、NPU完了セマフォおよび単調時刻によって処理順序と判定時間を安定させた点にある。評価時には、5fps周期が維持されているか、NPU待ちタイムアウトが発生していないか、カメラフレーム欠落時にタスクが過度に遅延していないかを確認する。
