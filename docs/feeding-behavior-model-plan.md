# 金魚 給餌行動学習モデル 計画書

**対象システム**: 相互守護アクアリウム（[docs/entry.md](./entry.md)）  
**担当サブプロジェクト**: `data_collector/`（データ収集ファーム）＋ Python 学習パイプライン  
**推論ターゲット**: EK-RA8P1（Arm Cortex-M85 + **Ethos-U55 NPU**）／メインアプリ `app/`  
**版**: v0.2（2026-09-27）

---

## 実行場所の境界

- **EK-RA8P1実機**: OV5640からのフレーム取得、金魚ボックス推論、フレーム差分による餌候補追跡、給餌状態機械、給餌検出、LCDへのデバッグ表示を実行する。
- メインアプリのRTOSは **μT-Kernel 3.0** とする。
- **PC**: 収集データの受信・保存、アノテーション、学習、モデル変換、オフラインの精度比較だけに使用する。実運用の画像検出と給餌判定はPCでは実行しない。

---

## 1. 目的

飼育者による給餌を、**沈下式の餌と1匹の金魚の位置関係**から検出できる軽量な画像処理・AI構成を作成する。本構成の出力（「給餌完了を確認した時刻」）を安否推定ロジックの主要トリガーとし、行動の途絶から異変を推定する。

### ゴール（成功基準）

- 給餌完了の見逃しを抑える。ただし、画像だけで断定できない場合は `unknown` を返し、誤った完了時刻を記録しない。
- 平常時の誤検出（False Positive）を実運用に耐える水準まで抑える。
- 金魚ボックス推定モデルを **Ethos-U55 上で INT8 量子化モデルとしてリアルタイム推論可能**にする。

> 金魚は1匹で、餌は沈下式である。水面への集合や魚群の活性化は主特徴にせず、餌候補の沈下軌跡と金魚ボックスへの接近・消失を主特徴とする。

### 未給餌監視と通知

- 最後に確認できた `feeding_completed` から **3日間** 給餌完了が確認されない場合、未給餌アラート状態とする。
- 開発・動作確認では判定閾値を **10分間** に短縮できるようにする。本番値とテスト値は設定で切り替える。
- `unknown` は給餌完了として記録せず、最後に確認した給餌時刻を更新しない。画像判定不能の状態は未給餌アラートと区別して表示する。
- 再起動後も3日間を正しく計測できるよう、最終給餌時刻と有効な時刻基準を保持する。時刻が未設定または無効な場合は未給餌判定を保留し、LCDに監視時刻不明を表示する。
- デバッグ状態、給餌完了、未給餌アラート、`unknown` はLCDに表示する。外部通信による通知は今回の対象外とする。
- 給餌イベント時刻と監視経過時間の管理はCPU側で行い、メインアプリはμT-Kernel 3.0上で動作する。

## 2. 問題設定

### 2.1 検出したい現象

給餌時に画像から確認する現象:

- フレーム差分で捉えられる餌候補の出現
- 餌候補の上から下への沈下軌跡
- 金魚ボックスと餌候補の距離の縮小
- 金魚の近傍での餌候補の消失
- 消失後、一定時間にわたる餌候補の非再出現

ここでは、**餌候補の検出**と**餌であることの確定**を分ける。色や単一フレームの変化だけで得られるものは餌候補であり、餌とは確定しない。餌の確定には、前フレームとの差分から同一候補を対応付け、複数フレームにわたる下方向の移動（沈降軌跡）を必須とする。

### 2.2 タスク定義

| フェーズ | タスク | 出力 |
|---------|--------|------|
| Phase 0 | 全画面候補抽出 + 前フレーム差分 + 餌候補追跡 + 状態機械 | 給餌判定のベースライン |
| Phase 1 | **単一金魚のボックス推定モデル** | `x, y, w, h, confidence` |
| Phase 2 | Phase 0 と Phase 1 の統合評価 | `feeding_completed` / `unknown` |

- **Phase 0を先に実装**し、餌が何フレーム見えるか、金魚への接近が観測できるかを確認する。
- 学習モデルは餌を直接検出しない。小さな餌はフレーム差分と追跡で扱い、モデルは金魚ボックスの推定に限定する。
- 濁り検出や水槽レイアウト変化検出は本モデルの対象外とする。

餌候補が見つかっただけでは `food_sinking` にしない。前フレーム差分による対応付けと下降軌跡が成立して初めて `food_sinking` とする。餌の軌跡が成立しない候補の消失は、給餌完了の根拠に使わず `unknown` または未確定のまま扱う。

### 2.3 固定する餌検出仕様

餌検出は固定ROIを使用せず、640x480の全画面を対象に次のCPU画像処理を行う。以下の処理順と状態遷移をPhase 0の固定方針とする。

#### 画像処理パイプライン

```text
RGB565/YUV422 frame
    -> 8-bit grayscale conversion
    -> consecutive-frame absolute difference
    -> upper 2% difference threshold (initial value)
    -> 3x3 morphological opening
    -> connected components
    -> small/large component rejection
    -> nearby fragment merge
    -> temporal association and downward-track validation
```

- **初期候補（seed）**: IDLE状態で全画面の暖色成分を調べる。8-bit RGBに変換した後、`min(R,G)-B > 15`、`max(R,G) < 210`、`min(R,G) > 20`を初期値とし、連結成分を候補にする。これは候補発見専用であり、餌確定には使わない。
- **動きの証拠**: フレーム$t$と$t-1$の8-bit輝度画像から `abs(I_t - I_{t-1})` を計算する。画面全体の差分値の上位2%を初期閾値とし、固定の明るさ閾値だけに依存しない。
- **ノイズ除去**: 3x3のオープニングで孤立した極小ノイズを除去する。連結成分は640x480で面積3未満を除外し、魚や水槽全体の変化に相当する大きすぎる成分も除外する。面積上限は実機画像で再測定する。
- **成分統合**: 餌の輪郭が分断された場合は、中心距離12px以内の成分を一つの候補へ統合する。固定ROIではなく、各フレームで得られた成分同士の動的な統合である。
- **2フレーム差分**: `abs(I_t - I_{t-2})` は一時的な見失いからの救済・対応付け補助に使ってよい。ただし、2フレーム差分だけで `food_confirmed` へ遷移させない。

#### 餌確定条件

候補を餌と確定するには、次の条件をすべて満たすことを要求する。

1. 初期候補が全画面から取得されている。
2. 次フレーム以降、前フレーム差分から同じ候補に対応する成分が取得されている。
3. 少なくとも2回連続して対応付けが成立している。
4. 対応する中心位置が時間方向に下へ移動している。移動量はフレーム間時間で正規化し、実機の5fpsと収録データの実測間隔を混同しない。
5. 横方向の移動量、成分面積、差分強度が設定した物理範囲内にある。
6. 画面全体の差分量が過大でなく、カメラ振動や照明変化が発生していない。

この条件を満たさないものは `food_candidate` に留め、餌として扱わない。対応付けが途切れた場合も、直前までの軌跡だけで餌確定や給餌完了を推定しない。

#### 状態遷移

```text
IDLE
  -> FOOD_CANDIDATE       : 全画面からseedを取得
FOOD_CANDIDATE
  -> TRACKING             : 次フレームの差分成分へ対応付け
TRACKING
  -> FOOD_CONFIRMED       : 2回以上連続した下降軌跡
TRACKING
  -> FOOD_CANDIDATE       : 一時的な対応付け失敗（短時間のみ）
TRACKING
  -> UNKNOWN              : 速度逸脱、全体振動、長時間の追跡断
FOOD_CONFIRMED
  -> CONSUMED_OR_OCCLUDED : 近傍で候補が消失
CONSUMED_OR_OCCLUDED
  -> FEEDING_COMPLETED    : 一定時間、候補が再出現しない
CONSUMED_OR_OCCLUDED
  -> UNKNOWN              : 再出現、遮蔽、底面残留などを確認
```

`FEEDING_COMPLETED` へ遷移できるのは、`FOOD_CONFIRMED` を経由した軌跡だけとする。色候補の出現、単発の差分、2フレーム差分単独、候補の消失だけでは給餌完了にしない。

### 2.4 ラベル付けの考え方

水質センサーは使用しない。給餌マーカーを基準時刻として候補区間を作り、餌候補・金魚ボックス・イベント状態を目視で確定する。

```text
[給餌マーカー] -> 前後の短いクリップを抽出
       -> 餌候補の軌跡、金魚ボックス、状態遷移をアノテーション
       -> マーカーなしの通常遊泳・反射・振動を負例として収集
```

## 3. データ収集計画（`data_collector/` ファーム）

### 3.1 収集データ

| データ | 取得元 | 形式 / レート |
|--------|--------|--------------|
| カメラ連続フレーム（学習素材） | OV5640 / MIPI-CSI2 | YUV422 -> RGB565、**5 fpsを初期値** |
| 給餌イベントマーカー | ユーザーボタン押下 | イベント時刻 |
| 環境メタデータ | 収集セッション | 時刻、照明状態、カメラ状態 |

### 3.2 保存・搬出方式

- **PCへの搬出**: USB High Speed / Ethernet(RGMII) 経由で、収集データをPCへ転送・保存する。PCはデータ保存先であり、実運用の検出処理は行わない。
- **オンボード蓄積**: 64MB OSPI Flash / SDHI(SDカード)に一時保存後、まとめて回収する。
- フレームバッファは64MB SDRAM上に確保する（64-byteアラインメント）。

### 3.3 データセット設計

- 撮影は640x480で保存し、金魚モデルの学習・推論時に **256x256グレースケール**へリサイズする。
- 金魚1匹の `x, y, width, height` と、見えにくい場合の可視性フラグを記録する。
- 餌候補の中心、フレーム間の対応、沈下・接近・消失・底面残留の状態を記録する。
- イベントラベルは `idle`、`food_sinking`、`fish_approaching`、`eating_candidate`、`feeding_completed`、`unknown` とする。
- 通常遊泳、泡・ゴミ、反射、照明変化、カメラ振動、餌が底に残った状態を負例に含める。
- train / validation / test は撮影セッション単位で分割し、隣接フレームのリークを防止する。

### 3.4 ファーム実装タスク

1. OV5640初期化・フレーム取得
2. 5 fpsを初期値とした連続フレーム収集
3. タイムスタンプとフレーム番号の付与
4. 給餌マーカー入力（ユーザーボタン）
5. PC（収集データの受信・保存のみ）または外部ストレージへの搬出

## 4. 学習・ラベル作成用前処理（PC側）

ここで行う処理は学習用データの準備とオフライン評価であり、実運用の検出処理ではない。

1. YUV422/RGB565をグレースケールへデコードする。
2. 金魚モデル用に256x256へリサイズし、ボックス座標を同じ比率で変換する。
3. 全画面の初期候補を抽出し、前フレーム差分から連続フレーム間で追跡する。2回以上の連続下降が成立した候補だけを餌確定ラベルの対象にする。
4. 給餌マーカーを基準に状態ラベルを目視で確定する。
5. 明度・コントラスト変動、軽微な反射、軽微な回転・クロップで拡張する。
   - 餌の沈下方向、金魚ボックス、カメラ固定条件を壊す変換は禁止する。

## 5. モデル設計

### 5.1 制約（Ethos-U55 / RA8P1）

- **INT8量子化必須**（Ethos-U55は8-bit整数演算）。
- Vela/RUHMIがサポートする標準的なConv2D、DepthwiseConv、Pooling、Flatten、FullyConnectedを使用する。
- モデルサイズとテンソルアリーナは、MRAM/SRAM/SDRAMの配置を実測して決める。

### 5.2 確定する構成

| 構成 | 特徴 | 用途 |
|------|------|------|
| フレーム差分 + 連結成分 + 最近傍追跡 | 餌を直接学習せず、沈下軌跡を扱える | **餌候補の主経路** |
| **小型単一物体ボックス回帰CNN** | 金魚1匹の `x, y, w, h, confidence` を出力 | **学習モデル** |
| 大型物体検出モデル | データ量・後処理・メモリが増える | 初期構成では不採用 |

金魚ボックスモデルの初期構成:

```text
Input       [1, 256, 256, 1]
Conv2D      16ch, 3x3, stride 2, ReLU
Depthwise   16ch, 3x3, stride 2, ReLU
Conv2D      32ch, 3x3, stride 2, ReLU
Depthwise   32ch, 3x3, stride 2, ReLU
Conv2D      64ch, 3x3, stride 1, ReLU
Flatten
 Dense       5 values: x, y, w, h, confidence
Output      [1, 5] float32  (学習時)
```

- `x`、`y`、`w`、`h`は画像サイズで正規化した値とする。`x`と`y`はbbox左上座標とする。
- 出力の活性化関数はモデル外で処理できるよう、最終出力はlinearを初期案とする。
- 餌の物体検出ヘッドは持たせない。
- 時系列はモデルへ持ち込まず、餌軌跡とボックス距離をCPU側の状態機械で処理する。
- RNN、3D-CNN、複数フレーム入力は初期構成では採用しない。

### 5.3 給餌完了の状態機械

```text
IDLE
  -> 全画面から餌候補が出現
FOOD_CANDIDATE
  -> 前フレーム差分で同一候補を対応付け
TRACKING
  -> 2回以上連続して下方向へ移動
FOOD_CONFIRMED (event_state=food_sinking)
  -> 金魚ボックスとの距離が縮小
FISH_APPROACHING
  -> 金魚近傍で確定済み餌候補が消失
EATING_CANDIDATE
  -> 一定時間、餌候補が再出現しない
FEEDING_COMPLETED
```

次の場合は `unknown` とする。

- 餌候補が底面で停止した。
- 餌候補が前フレーム差分で対応付けできず、連続下降が成立しない。
- 餌候補が金魚に隠れたが、消失後の再出現を確認できない。
- カメラ振動や照明変化でフレーム差分が全体的に増えた。
- 金魚ボックスまたは餌候補の追跡が途切れた。

金魚が餌候補へ近づくことは `FISH_APPROACHING` の条件であり、それだけで完了とはしない。金魚近傍での餌候補の消失と、一定時間の非再出現まで確認して完了とする。

## 6. 変換・デプロイ

```text
Keras/TFモデル
   -> TFLite Full INT8変換
        -> RUHMI / Velaコンパイル（Ethos-U55向け最適化）
             -> app/へ組み込み（Cortex-M85からNPU駆動）
                  -> カメラフレーム -> 金魚ボックス推定
                       -> 餌差分追跡 + 距離判定 + 状態機械
```

- モデル重みは容量に応じてコードフラッシュ、SDRAM、OSPI(XIP)を比較する。
- 推論結果と状態機械の状態を、安否推定ロジックおよびLVGL表示へ接続する。

## 7. 評価

### 7.1 モデル精度（PCでのオフライン評価）

- 金魚ボックスのIoU、中心位置誤差、confidenceの適合率・再現率を測定する。
- 給餌イベント単位のRecall、Precision、F1、誤完了率を測定する。
- 泡・ゴミ・反射・照明変化・カメラ振動・底面残留餌を誤検出分析に含める。
- この評価は実機で行う検出・給餌判定の代替ではなく、学習と変換の品質確認に用いる。

### 7.2 オンデバイス評価（EK-RA8P1実機）

- 推論レイテンシ（fps）とメモリ使用量（アリーナサイズ）を測定する。
- 5 fps入力でのフレーム取りこぼし数を記録する。
- EK-RA8P1上のNPU実行とCPU実行のボックス結果を比較する。

### 7.3 システム統合評価

- 餌候補の沈下、金魚への接近、近傍での消失、非再出現による給餌完了精度を測定する。
- 給餌していない通常遊泳で `feeding_completed` が発生しないことを確認する。
- 判定不能時に `unknown` となり、誤った最終給餌時刻を更新しないことを確認する。
- 最後の給餌完了から3日（テスト設定では10分）経過した場合だけ未給餌アラートになり、LCDに表示されることを確認する。

## 9. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| 学習データ不足・偏り | 汎化性能低下 | 撮影セッション、照明、餌量、魚の位置を分散する |
| 反射・照明変化 | 餌候補の誤検出増 | グローバル差分の除外、照明負例、しきい値調整 |
| 金魚の自発的遊泳 | 接近条件の誤成立 | 餌の沈下軌跡を必須条件にし、魚だけの動きでは成立させない |
| 餌が底に残る・魚に隠れる | 完了判定不能 | `unknown` として扱い、餌候補の再出現監視を続ける |
| 餌が小さすぎる | 軌跡欠落 | 5 fpsを初期値とし、撮影解像度と照明を見直す |
| NPU非対応オペレータ | 変換不可 | 標準演算子だけで構成し、Vela変換を早期に確認する |
| 見逃し（FN） | 安否確認の失敗 | Recall優先、完了判定の再試行、`unknown`を無給餌と同一視しない |
