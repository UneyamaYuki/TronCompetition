# 給餌行動データ収集ファームウェア 要件定義

## 1. 目的

EK-RA8P1 と OV5640 カメラを使用し、金魚の給餌行動を推定するための画像データセットを収集する。

給餌判定方式は現時点では確定しない。収集データは、少なくとも次の方式を比較・検証できるものとする。

- 画像分類モデルによる「給餌中 / 非給餌」の判定
- 物体検出モデルによる金魚の位置検出と、移動量・水面への集合度などのルールベース判定
- フレーム差分やオプティカルフローなど、機械学習を使わない画像処理による判定
- 複数フレームを入力する時系列モデルによる判定

本ファームウェア自身は給餌行動を判定せず、方式選定と学習・評価に必要な一次データを欠損なく収集することを責務とする。

## 2. スコープ

### 2.1 対象

- OV5640 からのカメラ画像取得
- 一定周期での連続フレーム収集
- 給餌操作を示す手動イベントマーカーの記録
- 画像とメタデータへの共通タイムスタンプ付与
- PC または外部ストレージへのデータ搬出
- 収集状態と異常の通知

### 2.2 対象外

- 水質センサー（TDS、pH など）の接続、記録、ラベル生成
- Ethos-U55 による推論
- 給餌行動の最終判定
- 安否推定および外部へのアラート通知
- 水槽環境の自動制御

## 3. 収集対象

給餌の前後を含む連続画像を収集し、以下の特徴を後から解析できるようにする。

- 金魚の位置、数、見かけの大きさ
- 水面付近への集合
- 移動方向、移動量、速度の変化
- 餌をついばむ際の局所的な動き
- 水面の揺れや反射
- 給餌前、給餌中、給餌後の時間変化

非給餌時についても、通常遊泳、活発な遊泳、照明変化、清掃、人影やカメラ振動など、誤検出要因を含む画像を収集する。

## 4. 機能要件

### FR-01 カメラ初期化

- EK-RA8P1 に接続した OV5640 を初期化し、MIPI-CSI2 経由で画像を取得できること。
- 初期化失敗を検出し、利用者に通知できること。

### FR-02 連続画像取得

- 設定したフレームレートで連続画像を取得できること。
- 初期仕様は 640×480、YUV422、5 fps でカメラ画像を取得し、JPEG に圧縮して保存・転送すること。
- JPEG 圧縮には RA8P1 内蔵 JPEG Codec と FSP `r_jpeg` のエンコード機能を使用し、ソフトウェア JPEG エンコーダーは使用しないこと。
- JPEG 品質は 85 相当を初期目標とし、量子化テーブルをビルド設定で変更可能とすること。
- フレームレートは少なくとも 1 fps、2 fps、5 fps を選択可能とすること。
- 学習用の縮小画像だけでなく、後から前処理やアノテーション方法を変更できる解像度で保存すること。

### FR-02A JPEG 圧縮

- JPEG Codec への入力は YCbCr 4:2:2、640×480、2 bytes/pixel とすること。
- 入力フレームバッファと JPEG 出力バッファは SDRAM に配置し、FSP が要求する 8-byte 以上のアラインメントを満たすこと。
- JPEG 出力はフレームごとの可変長データとして扱い、実際の圧縮後サイズをメタデータと USB フレームヘッダーに記録すること。
- 圧縮処理はカメラ取得と USB 転送から分離し、少なくとも 2 面の入力バッファと複数の JPEG 出力バッファを用いて処理待ちを吸収すること。
- JPEG の SOI (`FFD8`) と EOI (`FFD9`) を確認し、不正な圧縮データを PC へ正常フレームとして送信しないこと。
- JPEG Codec のタイムアウト、出力バッファ不足、エンコードエラーを検出し、対象フレーム番号とエラー理由を記録すること。
- 5 fps の期限内に圧縮が完了しない場合は未圧縮画像へ切り替えず、対象フレームを欠落として記録すること。

### FR-03 撮影セッション管理

- 専用の収集操作ボタンを押すことで、待機中は新しい収集セッションを開始し、収集中はそのセッションを停止できること。
- ボタンは短押し 1 回で開始または停止を受け付け、長押しや押し続けによる連続切り替えを発生させないこと。
- ボタン入力にはチャタリング除去を行い、押下後にボタンが解放されるまで次の操作を受け付けないこと。
- 電源投入およびカメラ初期化完了後の初期状態は待機中とし、利用者がボタンを押すまで画像を保存しないこと。
- 収集開始から終了までを一意なセッションとして管理すること。
- セッション開始時に一意なセッション ID を生成または設定できること。
- セッションごとに画像、イベント、設定、エラーを対応付けられること。
- 停止操作を受け付けた後は新しいフレームの取得・保存を停止し、処理中の書き込みとメタデータを確定してから待機状態へ戻ること。
- 終了処理中のボタン操作は無視し、二重終了や直後の意図しない再開を防ぐこと。

状態遷移は以下を基本とする。

```text
[初期化中] --初期化完了--> [待機中]
[待機中]   --ボタン短押し--> [収集中]
[収集中]   --ボタン短押し--> [終了処理中]
[終了処理中] --保存確定-->   [待機中]
```

### FR-04 タイムスタンプ

- すべてのフレームに、セッション開始からの単調増加時刻を付与すること。
- タイムスタンプの単位はミリ秒とすること。
- フレーム番号はセッション内で単調増加し、欠番を検出できること。
- RTC を利用できる場合は実時刻も記録するが、必須とはしない。

### FR-05 給餌イベントマーカー

- 収集開始・停止ボタンとは別のボタンまたは入力手段で、給餌時刻を記録できること。
- ボタン押下時刻を画像と同じ時間基準で記録すること。
- チャタリング除去を行い、1 回の操作を 1 イベントとして記録すること。
- 誤操作を後処理で識別できるよう、イベントには連番を付与すること。

手動マーカーは正解ラベルそのものではなく、アノテーション候補区間を抽出するための基準時刻として扱う。

### FR-06 メタデータ記録

各セッションについて、最低限以下を記録すること。

- データ形式のバージョン
- セッション ID
- 撮影解像度
- ピクセル形式
- 設定フレームレート
- セッション開始・終了時刻
- 総取得フレーム数
- 欠落フレーム数
- 給餌イベント一覧
- ファームウェアのバージョンまたはビルド識別子

各フレームについて、最低限以下を対応付けること。

- フレーム番号
- タイムスタンプ
- JPEG データの長さ
- JPEG 品質設定の識別子
- 画像データの整合性確認値

### FR-07 データ搬出

- EK-RA8P1 の USB High Speed Device ポートと PC を USB ケーブルで接続し、画像とメタデータをリアルタイム搬出できること。
- USB CDC-ACM（仮想 COM ポート）を使用し、Windows の標準ドライバーで認識できること。
- CDC のデータ部分には、フレーム、給餌イベント、セッション情報、エラー情報を識別できるバイナリプロトコルを使用すること。
- 1 フレームを複数の USB 転送単位に分割でき、PC 側でフレーム番号とデータ長に基づいて再構成できること。
- PC の収集ツールが USB ポートをオープン済みの場合のみ収集を開始し、未接続時の開始操作はエラーとして通知すること。
- USB 切断を検出した場合は新しいフレームの取得・転送を停止し、セッションを異常終了として記録すること。
- 保存または転送が画像取得に追いつかない場合、フレームを無言で上書きしないこと。
- 欠落したフレーム数と発生時刻を記録すること。
- PC 側で機械的に読み取れる、仕様が固定された形式を使用すること。

### FR-08 状態通知

最低限、以下の状態を LED、LCD、またはデバッグコンソールで識別できること。

- 初期化中
- 待機中
- 収集中
- 終了処理中
- 給餌マーカー受付
- 搬出待ちまたは書き込み中
- カメラ異常
- バッファ不足または転送異常
- ストレージ容量不足（ストレージ方式の場合）

### FR-09 正常終了と復旧

- 利用者の終了操作により、書き込み途中のデータを確定してセッションを正常終了できること。
- 通信断や書き込み失敗を検出し、エラーとして記録すること。
- 異常終了したセッションについて、正常に保存済みの範囲を識別できること。

## 5. データ要件

### 5.1 保存単位

データはセッション単位で保存し、同一セッション内に以下を含める。

- 連続フレーム
- 給餌イベントログ
- セッションメタデータ
- 欠落・通信・保存エラーログ

具体的なコンテナ形式は搬出方式の技術検証後に決める。画像とログの対応をファイル名だけに依存させず、フレーム番号とタイムスタンプで関連付ける。

### 5.2 アノテーション可能性

データは後処理で次のラベルを追加できる構造とする。

- `feeding` / `not_feeding` の区間ラベル
- 金魚ごとのバウンディングボックス
- 水面領域
- 通常遊泳、給餌反応、清掃、照明変化などのイベント種別

ファームウェアはこれらの推定ラベルを画像へ焼き込まない。

### 5.3 データセット分割

学習時はフレーム単位で無作為分割せず、撮影日または撮影セッション単位で train / validation / test に分割できること。そのため、セッション ID と撮影条件を保持する。

## 6. 非機能要件

### NFR-01 データ完全性

- 保存済みデータの破損を検出できること。
- フレーム欠落とイベント欠落を後から確認できること。
- 長時間収集時にもフレーム番号とタイムスタンプが重複しないこと。

### NFR-02 リアルタイム性

- カメラ取得処理を、低速な保存・通信処理から分離すること。
- SDRAM 上の複数バッファを使用し、取得中フレームを保存処理が破壊しないこと。
- 目標フレームレートを維持できない場合は、その事実を測定・記録すること。

### NFR-03 拡張性

- フレームレート、解像度、ピクセル形式、搬出方式を設定として変更できる構造にすること。
- 将来モデル方式を変更しても、収集済みの元画像を再利用できること。
- 将来センサーを追加する場合も、既存の画像・イベント形式を壊さず新しいログ種別を追加できること。ただし現版では水質センサーを実装しない。

### NFR-04 保守性

- FSP 生成物 (`ra_gen/`, `ra_cfg/`, `ra/`) を直接編集しないこと。
- `test/` の OV5640、MIPI-CSI2、SDRAM 実装を参照し、手書きコードと生成コードを分離すること。
- データ形式にはバージョンを付け、PC 側ツールとの互換性を管理すること。

### NFR-05 プライバシー

- カメラは水槽内を撮影し、飼育者の顔や生活空間を意図的に撮影しないこと。
- 画像の外部送信を行う場合、送信先と保存場所を利用者が把握できる構成とすること。

## 7. 収集条件

モデル方式を選定できるだけの比較データを得るため、以下の条件を分散して収集する。

- 給餌前、給餌中、給餌後
- 朝、昼、夜
- 照明の点灯・消灯、外光の変化
- 餌の量や投入位置の違い
- 金魚の通常遊泳と自発的な活発化
- 水面反射、泡、フィルターによる水流
- 可能な範囲で異なる撮影日、水槽状態、個体配置

各給餌セッションは、給餌前の通常状態と給餌後の収束過程を含む時間幅で記録する。具体的な前後時間は予備撮影で金魚の反応時間を確認して決定する。

## 8. 受け入れ基準

最初の実用版は、以下をすべて満たした時点で受け入れとする。

1. EK-RA8P1 起動後に OV5640 を初期化し、連続画像を取得できる。
2. 初期化完了後は待機状態となり、収集操作ボタンの短押しで収集を開始できる。
3. 収集中に同じボタンを短押しすると、データを確定して待機状態へ戻ることができる。
4. 待機中、終了処理中、またはボタンを押し続けている間に、意図しない収集開始・停止が発生しない。
5. 5 fps で 10 分間の収集試験を完走できる。
6. 取得した YUV422 フレームを RA8P1 の JPEG Codec で圧縮し、PC 側の標準的な JPEG デコーダーですべての正常フレームを 640×480 画像として復号できる。
7. JPEG 圧縮時間、圧縮後サイズ、品質設定をフレーム単位またはセッション統計として確認できる。
8. 各フレームをフレーム番号およびミリ秒タイムスタンプと対応付けられる。
9. 収集中に複数回の給餌マーカーを記録し、対応する画像区間を PC 側で抽出できる。
10. 取得フレーム数、圧縮成功数、保存フレーム数、欠落フレーム数が一致して説明可能である。
11. 保存データの破損または欠落を PC 側で検出できる。
12. 異常終了後も、正常に保存された範囲を識別できる。
13. 水質センサーなしで、画像・手動マーカー・メタデータのみからデータセットを構築できる。

## 9. 未決定事項

### 9.1 確定事項

| 項目 | 決定内容 |
|---|---|
| 搬出方式 | USB High Speed Device によるリアルタイムストリーミング |
| USB クラス | CDC-ACM（Windows の仮想 COM ポート） |
| 初期撮影設定 | 640×480、YUV422、5 fps で取得し、JPEG 品質 85 相当で圧縮 |
| RTOS | FreeRTOS |
| 収集操作 | オンボード USER SW1 の短押しで開始・停止 |
| 給餌マーカー | オンボード USER SW2 の短押しで記録 |
| 時刻 | セッション開始からの単調増加ミリ秒。RTC 実時刻は使用しない |

### 9.2 実装中に決定する事項

| 項目 | 候補 | 決定に必要な確認 |
|---|---|---|
| USB 上のデータ形式 | 固定長ヘッダー + ペイロード | 再同期、破損検出、後方互換性 |
| JPEG 量子化テーブル | 品質 85 相当を初期値とする | 金魚の輪郭・色・微細な動きとファイルサイズの比較 |
| JPEG 出力バッファ容量 | 予備撮影の最大圧縮サイズから決定 | バッファ不足を発生させない安全率と SDRAM 使用量 |
| CDC 転送単位とキュー長 | FSP USB ドライバーの制約に合わせる | JPEG の可変長連続転送性能と SDRAM 使用量 |
| 収集時間幅 | 給餌前後の秒数・分数 | 予備撮影での反応開始・収束時間 |

## 10. 実装方針

- 実装先は `data_collector/` とする。
- RTOS は FreeRTOS とし、`test/` の既存プロジェクト構成を流用する。
- `test/e2studio/src/camera_thread_entry.c` をカメラ取得の主要な参照元とする。
- オンボード USER SW1 を収集開始・停止、USER SW2 を給餌マーカーに使用し、既存の外部 IRQ 設定を流用する。
- 大容量フレームバッファは SDRAM に配置し、既存実装のアラインメントとキャッシュ管理を踏襲する。
- FSP で JPEG Codec (`r_jpeg`) のエンコード機能を追加し、OV5640 から取得した YUV422 フレームをハードウェア圧縮する。
- FSP で USB High Speed Device と CDC-ACM を追加し、ボードの USB HS ロールを Device に設定する。
- 最初にダミーの YUV422 フレームを使い、JPEG 圧縮時間、最大圧縮サイズ、圧縮後の USB 転送量を測定する。
- カメラ接続後、640×480、5 fps の JPEG ストリームを 10 分間継続搬出できることを検証する。
- PC 側には Python で受信ツールを実装し、仮想 COM ポートからバイナリデータを読み取って画像とメタデータを保存する。
- データ収集段階では画像を過度に縮小・加工せず、学習用変換は原則として PC 側で行う。
